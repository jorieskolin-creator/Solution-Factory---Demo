CSCF / Technical architecture / Reference blueprint

Continuous Solution Creation Flow

An end-to-end, vertically traced blueprint of how purpose and evidence become bounded software change, how code and applicable obligations are independently verified, and how production evidence governs the next state.

The pipeline standardizes how a change is understood, constrained, executed, verified, remediated and authorized. It does not standardize the solution or make a coding agent the control architecture.

Reading legend

DETERMINISTIC means executable rules, schema checks, scanners, exact mappings or recorded authority checks. AI-ASSISTED means bounded probabilistic drafting, interpretation or exploration, never self-approval. GATE is an evidence/authority decision, not simply the end of a conventional process phase.

Source-derived design versus suggested detail: CSCF's kernel, dual contracts, independent verification, assurance scopes, tactics, agent adapters and validated learning follow the current conceptual design. The numbered split, field names and interface examples below are an illustrative technical elaboration, not a claim that these exact schemas or services already exist in production.

GOVERNED FOUNDATION

Governed foundation

Maintained control plane, not an AI agent

00
GOVERNED FOUNDATION

Maintain the creation system

What controls the pipeline itself?

Input
Approved system-model version, policy sources, schema catalogue, tool adapters, authorized roles, prior pipeline evaluation.
Transformation / action
The Maintainer maintains the kernel, schemas, knowledge/control packs, tactic mappings, gates, executor adapters, validation cases and their own change history. Validate updates to the creation system before they are activated.
Deterministic responsibility
Schema and reference checks, package version/hash checks, authorization lists, policy precedence, regression tests on golden and failure cases.
Where AI may help — bounded
AI may draft candidate knowledge objects, propose control changes, analyze failure patterns or suggest tactics. Those proposals are not automatically approved.
Knowledge sources / packs
Canonical control KB, approved source register, Tactic Playbook, system knowledge, assurance instrument, workflow policy.
Schema / typed objects
KernelConfig · PolicyPackManifest · KnowledgeObject · TacticDefinition · ChangeApproval
Output
A versioned, validated runtime policy snapshot and operating boundaries for one CSCF run.
Progression / decision gate

If required source authority, mapping, gate implementation or approval is unavailable, the affected workflow cannot be declared ready.

Failure path / loop

→ Repair or approve the deficient policy/configuration package. Do not ask a coding agent to waive its own control.

Architecture note +

This foundation is persistent. It is not re-created by the LLM for each coding task. Source authority, knowledge status and execution permissions are different objects.

INTAKE & REALITY

Intake & established reality

Build bounded evidence before reasoning

01
INTAKE & REALITY

Register change intent and entry mode

Is this a new solution or a change to an existing one?

Input
User/customer demand, defect report, incident, opportunity, legal change or maintenance trigger; target system or proposed new solution.
Transformation / action
Create a change identity, accountable owner, purpose statement, expected outcome, priority and delivery context. New build starts with a target-state hypothesis. Existing solution change starts from the accepted current state.
Deterministic responsibility
Identity assignment, mandatory-field/type checks, timestamping, ownership checks, duplicate detection and initial scope classification.
Where AI may help — bounded
AI can help clarify a vague request and propose questions. It cannot silently transform a hypothesis or stakeholder preference into an approved requirement.
Knowledge sources / packs
Product/domain policy, prior accepted requirements, customer commitments, solution register.
Schema / typed objects
ChangeIntent · PurposeHypothesis · StakeholderAuthority · EntryMode
Output
Registered ChangeIntent with declared facts, unknowns, intended outcome and accountable owner.
Progression / decision gate

If the purpose or target system is unidentifiable, do not create an executable contract.

Failure path / loop

→ Return clarification questions to a named human/domain owner.

Architecture note +

Output carries provenance and epistemic state: DECLARED, OBSERVED, INFERRED or UNKNOWN. “New build” and “change request” merge into one controlled mechanism after intake.

02
INTAKE & REALITY

Acquire sources safely and register evidence

Which files and observations are admissible?

Input
Repository and commit/branch, API/interface definitions, ADRs, diagrams, tests, CI findings, operations data, customer documentation, relevant regulations and approved policies.
Transformation / action
Select and safely inspect source material. Register source ID, version/commit, path/locator, hash, extraction method, trust class, freshness, limitations and coverage. Distinguish customer-provided assertions from observed code/configuration and executed test results.
Deterministic responsibility
Content hashing, file/type checks, archive and secrets screening, DLP/redaction where needed, extraction coverage, permission checks, immutable evidence ledger creation.
Where AI may help — bounded
AI may help find semantic relationships or summarize sanitized, bounded packets. Repository comments, issue text and external files are treated as untrusted data, not instructions.
Knowledge sources / packs
Evidence-acquisition policy, data-classification and privacy rules, source authority register, repository/asset inventory.
Schema / typed objects
SourceRecord · EvidenceItem · SourceLocator · ExtractionResult · DataClassification
Output
Provenance-linked evidence inventory and list of inaccessible, excluded or contradictory sources.
Progression / decision gate

Material missing evidence or unsafe handling blocks fact promotion and may block progression.

Failure path / loop

→ Targeted re-read, human-approved access, alternate acquisition, or mark the relevant conclusion UNKNOWN.

Architecture note +

For privacy and confidentiality, controls govern what may leave a protected boundary. Raw proprietary code or personal data is not automatically suitable for an external model.

03
INTAKE & REALITY

Construct the evidence-backed system state

What is actually implemented and known?

Input
Validated source ledger, prior accepted SystemState, code and dependency graph, architecture records, test/run results, known defects and operational observations.
Transformation / action
Create or refresh the governed SystemState. Map components, APIs, data flows, roles, permissions, invariants, unresolved findings, deployment and version boundaries. Keep declared, implemented, tested and operationally observed claims distinct.
Deterministic responsibility
Repository indexing, dependency extraction, schema comparisons, source-to-claim referential integrity, conflict detection and version matching.
Where AI may help — bounded
AI may propose a system explanation, classify interfaces or flag contradictions. Its proposed facts require attributable corroboration before being used as decision-eligible facts.
Knowledge sources / packs
System-model KB, architectural decision records, component catalogue, verified historical evidence.
Schema / typed objects
SystemState · ComponentGraph · Invariant · FactClaim · EvidenceLink
Output
Version-specific current or hypothesized SystemState with fact status, provenance, gaps and confidence limits.
Progression / decision gate

The system model cannot silently invent unknown dependencies or present an untested control as effective.

Failure path / loop

→ Re-acquire evidence or constrain the assessed scope; unresolved critical facts block later contracts.

Architecture note +

The system model is maintained in the architecture, not reconstructed from a model context window on every turn.

QUALIFICATION

Qualification & applicability

Turn context into explicit obligations

04
QUALIFICATION

Determine impact boundary and materiality

What may this change affect beyond the edited lines?

Input
ChangeIntent, SystemState, dependency relationships, data flows, interface schemas, inherited constraints and impact questions.
Transformation / action
Identify target component plus its dependency neighborhood and global invariants. Trace downstream/upstream effects across data, users, security, interfaces, business rules, operations and architecture. Assign provisional materiality and uncertainty.
Deterministic responsibility
Graph traversal, path/permission comparison, schema diff, changed-API detection, classification rules, coverage/unknown accounting.
Where AI may help — bounded
AI may propose hidden coupling and questions for targeted evidence retrieval. It must not declare a critical dependency absent merely because none was retrieved.
Knowledge sources / packs
Architecture KB, domain rules, dependency inventory, security and privacy classifications, historical incidents.
Schema / typed objects
ImpactAssessment · AffectedSystemSlice · MaterialityProfile · OpenQuestion
Output
Bounded affected-system slice, materiality triggers and unresolved impact questions.
Progression / decision gate

Material uncertain dependencies prevent an unrestricted implementation plan.

Failure path / loop

→ Targeted discovery; if a change later exceeds the assessed boundary, return here with the new evidence.

Architecture note +

Example: changing a delivery address can affect tax, fraud rules, fulfilment, customer authorization, audit and event schemas even when the initial code diff is local.

05
QUALIFICATION

Compile applicable obligations

Which policy, engineering, privacy and legal requirements actually apply?

Input
Change properties, system purpose, affected data types, jurisdictions, role/actor classification, users, AI autonomy, customer commitments, target lifecycle stage.
Transformation / action
Evaluate each source-defined applicability rule. Preserve source identity, clause/locator, authority tier, version, jurisdiction/time limits, triggering facts, exclusions and unknowns. Activate relevant security, privacy, AI governance, accessibility, resilience, architecture and domain packs.
Deterministic responsibility
Typed applicability predicates, version/effective-date checks, reference validation, contradictory-policy detection, non-bypassable mandatory baseline and precedence rules.
Where AI may help — bounded
AI can help extract candidate obligations or explain ambiguous clauses. It cannot independently determine contested legal applicability or certify compliance.
Knowledge sources / packs
Normative-source register + approved clause mappings; security control KB; privacy/GDPR pack; AI governance A–F pack; customer/domain policies.
Schema / typed objects
ApplicabilityRecord · ActiveObligation · NormativeSourceRef · ControlPackBinding
Output
Exact active-obligation set, justified non-applicable decisions and a ledger of conditional or unresolved obligations.
Progression / decision gate

UNDETERMINED legal or safety-critical applicability is not PASS. Escalate or restrict the operating boundary.

Failure path / loop

→ Named policy, legal, DPO or domain authority resolves contested scope. Reclassify if the implementation changes the relevant facts.

Architecture note +

A control can be both mandatory and conditional. For example, personal-data processing triggers privacy obligations, while the need for a formal DPIA depends on the applicable legal risk threshold and policy, not on a universal assumption.

06
QUALIFICATION

Approve purpose, desired outcome and acceptance basis

Are we solving an approved problem rather than merely building code?

Input
Change hypothesis, affected user groups, baseline metrics, candidate success conditions, allowed/prohibited uses, source-backed risks and active obligations.
Transformation / action
Convert intent into a testable, accountable statement of purpose, outcome and boundaries. Distinguish functional acceptance from value/purpose acceptance and from security/legal compliance. Seek owner confirmation when needed.
Deterministic responsibility
Requirement completeness, uniqueness, traceability, consistency and measurable-criterion checks.
Where AI may help — bounded
AI may elicit acceptance questions, draft edge cases or compare alternatives. Business purpose and material trade-offs remain accountable human decisions.
Knowledge sources / packs
Purpose/value KB, product constraints, customer acceptance criteria, solution and governance policies.
Schema / typed objects
ApprovedRequirement · AcceptanceCriterion · PurposeBoundary · OwnerDecision
Output
Approved ChangeBaseline: goal, valid use, measurable success, exclusions, explicit assumptions and owner.
Progression / decision gate

Vague, contradictory or unapproved material acceptance criteria block contract-ready state.

Failure path / loop

→ Human/domain clarification or reformulation of the change hypothesis.

Architecture note +

The purpose gate is intentionally separate from tests. A technically valid implementation may still be the wrong intervention.

CONTRACT COMPILATION

Contract compilation

Implementation permission and independent proof

07
CONTRACT COMPILATION

Create two independently derived contracts

What may be changed, and separately, what must be proven?

Input
Approved ChangeBaseline, SystemState, AffectedSystemSlice, active obligations, architecture invariants and available evidence.
Transformation / action
Derive an Implementation Contract bounding actions, files/interfaces, privileges and invariants. Independently derive a Verification Contract requiring observable demonstrations, test types, negative cases, regulatory and security evidence, acceptance, provenance and decision limits.
Deterministic responsibility
Contract schema validation, complete obligation coverage, requirement/criterion mapping, prohibited-path checks, independent-branch consistency checks.
Where AI may help — bounded
AI may draft candidate constraints, test ideas or scenarios under bounded schemas. The same execution agent must not define its own sole success conditions.
Knowledge sources / packs
Engineering standards KB, policy/control packs, test-pattern KB, architecture KB, verification and assurance requirements.
Schema / typed objects
ImplementationContract · VerificationContract · RequirementControlTrace
Output
Two versioned contracts referencing the same approved requirement and separately describing permitted work versus required proof.
Progression / decision gate

Missing essential evidence condition, unsupported rule mapping or conflict prevents CONTRACT_READY.

Failure path / loop

→ Return to evidence acquisition, applicability, requirements or human approval as required.

Architecture note +

Contracts are machine-readable governed objects, not long prompts. They establish the work boundary and independent definition of done.

08
CONTRACT COMPILATION

Check contract readiness and publish bounded work packet

Is execution authorized to begin?

Input
Both contracts, completeness report, facts and unknowns, approved constraints, repository and data permissions.
Transformation / action
Evaluate contract integrity and all prerequisite gates. Construct the minimal relevant system slice, reference IDs, protected paths, tool policy and expected output fields as a signed/versioned WorkPacket.
Deterministic responsibility
Rule-engine checks: coverage, signature/hash, effective policy version, material unknowns, scope permissions, gate readiness and authority references.
Where AI may help — bounded
AI must not clear this gate. A model can explain why a contract is blocked but cannot change the gate result.
Knowledge sources / packs
Kernel transition rules, access policy, contract schema catalogue, control-pack manifest.
Schema / typed objects
ContractReadinessDecision · WorkPacket · ExecutionPermissionEnvelope
Output
CONTRACT_READY and bounded packet, or BLOCKED/ESCALATED with exact failed conditions.
Progression / decision gate

Only CONTRACT_READY may enter executor routing. Material change may still require the next planning gate.

Failure path / loop

→ Repair specific contract/evidence defects. Do not run a speculative agent with missing mandatory rules.

Architecture note +

Suggested state vocabulary: DRAFT → VALIDATED → APPROVED → CONTRACT_READY. Actual names are implementation details.

Condition: is planning required?

Low-risk, fully bounded change: a direct execution route may be allowed. Material or sensitive change: the independent Plan Gate must pass before an agent or human receives the write-capable work packet.

EXECUTION CONTROL · CODE GENERATION / MODIFICATION

Bounded execution

CSCF selects and authorizes an executor. The actual source-code changes happen here, in Step 10, not in the kernel or the contract-generation steps.

STEP 09 · SELECT EXECUTOR / AUTHORIZE PLAN · NO CODE WRITTEN YET
09
EXECUTION CONTROL

Route the execution capability and check plan

Which executor is suitable, and is its proposed plan permitted?

Input
Contract-ready WorkPacket, task type, code sensitivity, change materiality, available approved human/tool/agent adapters.
Transformation / action
Select human, deterministic tool or coding agent by capability, confidence, cost, complexity and risk. For material changes request a bounded step plan. Verify intended files, dependencies, privileged operations, testing and rollback before granting write access.
Deterministic responsibility
Executor allowlist, policy matching, sandbox/tool permission calculation, plan-vs-contract diff, prohibited-operation detection.
Where AI may help — bounded
An agent can propose an implementation plan but cannot authorize its own extra permissions, prohibited files, new risks or unreviewed architecture changes.
Knowledge sources / packs
Executor capability registry, secure-execution policy, coding standards, tool configuration KB, applicable human-review rules.
Schema / typed objects
ExecutorSelection · ExecutionPlan · PlanGateDecision · ToolPolicy
Output
Approved executor route and either an approved plan or a direct low-risk execution authorization.
Progression / decision gate

Sensitive operation or plan beyond scope yields PLAN_BLOCK or HUMAN_REVIEW_REQUIRED.

Failure path / loop

→ Narrow plan, expand authorized contracts, or escalate before write access.

Architecture note +

No agent-specific orchestration becomes a kernel invariant. The adapter may be changed without redefining contract semantics.

STEP 10 · CODE WRITING / MODIFICATION OCCURS HERE
10
EXECUTION CONTROL

Trigger the executor under a restricted envelope

Exactly what does the coding agent receive?

WHERE CODE IS ACTUALLY PRODUCED

INPUT · CREATED AND AUTHORIZED BY CSCF Approved execution work packet

Implementation Contract · relevant system slice · allowed files and tools · scoped workspace permissions

↓
ROUTING / ENFORCEMENT CSCF execution adapter

Translates the canonical packet into the chosen tool's format. Enforces sandbox, identity, network, credentials and execution limits.

↓
ACTUAL SOURCE-CODE AUTHORING · EXECUTION CAPABILITY CODING AGENT — writes and modifies code
Amp · Cursor · Augment Code · another approved agent

The selected agent reads the permitted repository slice, edits permitted source/configuration files, may create tests, and runs authorized development tools within its isolated workspace.

Can produce code and test artifacts. Cannot approve, merge, accept risk or authorize deployment.
↓
OUTPUT · NOT YET ACCEPTED Candidate code change

Code diff / patch · modified files · generated tests · dependency changes · assumptions · tool logs · provenance

↓
RETURN TO CSCF CONTROL Step 11 capture → independent verification

CSCF validates the candidate and determines whether to pass, block, request targeted rework or escalate. The agent never self-certifies its output.

Alternative route: CSCF may select a human developer or deterministic tool instead of an AI coding agent. The same implementation boundaries, result contract and independent verification still apply.

Input
Approved WorkPacket, Implementation Contract, relevant system slice, ToolPolicy, repository snapshot, allowed endpoints and limits.
Transformation / action
Adapter translates canonical packet to the selected executor format and invokes it with scoped workspace access, time/resource budgets, short-lived credentials and auditable calls. Keep policy instructions isolated from retrieved documents and code comments.
Deterministic responsibility
Credential minting, isolated workspace creation, network/file allowlists, runtime audit collection, model/tool version pinning and input/output schema enforcement.
Where AI may help — bounded
A coding model may edit permitted files, run permitted tools and report uncertainties. It is only an executor and receives no authority to merge, approve, accept risk or deploy.
Knowledge sources / packs
Coding/risk-control KB, selected architecture slice, secure-coding pattern library, executor prompt/tool governance.
Schema / typed objects
InvocationRecord · ExecutorEnvelope · WorkPacket · ToolCallAudit
Output
An attributable execution attempt with its own invocation ID, policies, time limits and trace.
Progression / decision gate

Untrusted instruction injection, unauthorized tool call, secret exposure or boundary violation stops execution and produces an incident/finding.

Failure path / loop

→ Contain, revoke credentials, preserve evidence and reclassify the attempt. A retry must use corrected validated inputs.

Architecture note +

Canonical invocation interface: execute(implementation_contract, relevant_system_slice, tool_policy, repository_access) → ImplementationResult. The Verification Contract is protected from becoming an agent-editable success definition.

STEP 11 · CAPTURE CANDIDATE CODE · NO ACCEPTANCE YET
11
EXECUTION CONTROL

Capture candidate change without promoting it

What did the executor actually change?

Input
Patch/commit, changed files, generated tests, dependency updates, tool logs, assumptions, warnings and executor report.
Transformation / action
Normalize the candidate to a strict ImplementationResult. Record hashes, changed paths, changed APIs/configurations, test origins, assumptions, unresolved questions and exact run provenance. Treat all agent prose as candidate claims.
Deterministic responsibility
Patch validation, schema/types, file path safety, provenance checks, sensitive-file detection and repository state comparison.
Where AI may help — bounded
AI may summarize its work or identify possible side effects. Its self-reported “tests pass” and “secure” claims have no independent evidentiary status.
Knowledge sources / packs
ImplementationResult schema, repository and evidence policy, relevant test/invariant catalogue.
Schema / typed objects
ImplementationResult plus immutable CandidateChange ledger and explicit unsupported/unknown claims.
Output
A malformed or out-of-bounds result cannot proceed as a valid candidate.
Progression / decision gate

→ Return a bounded defect code to the executor or reopen scope if the actual impact is material.

Failure path / loop

“Code produced” is never synonymous with accepted software or a valid system-state transition.

Architecture note +

INDEPENDENT VERIFICATION

Independent verification

Prove code, behavior and control implementation

12
INDEPENDENT VERIFICATION

Run structural and software supply-chain checks

Does the result satisfy mechanically verifiable constraints?

Input
Candidate patch/commit, required policy checks, expected schemas, toolchain and build environment.
Transformation / action
Compile/typecheck/lint; validate API/schema changes, forbidden paths, supply-chain and dependency policy; run SAST, SCA, secrets scanning, IaC/config/container scanning, SBOM and artifact integrity checks where applicable.
Deterministic responsibility
Build/CI tools, scanners, cryptographic signature checks, checksums, dependency analyzers and deterministic break conditions.
Where AI may help — bounded
AI can help triage warnings and propose bounded fixes but cannot turn a failed scanner into a pass.
Knowledge sources / packs
Static-check policy, secure-coding KB, vulnerability and supplier rules, signed-control manifest.
Schema / typed objects
CheckResult · ScanFinding · SBOM · BuildArtifact · StructuralEvidence
Output
Reproducible pass/fail/unknown results linked to exact revision and scanner/config versions.
Progression / decision gate

Any applicable mandatory hard-fail yields BLOCK unless an authorized, scoped exception is recorded.

Failure path / loop

→ Tactic routing for repair. High-risk exceptions are explicit human authority actions.

Architecture note +

A clean scan only establishes that the activated checks did not detect their targeted conditions; it is not proof that the system is secure or legally compliant.

13
INDEPENDENT VERIFICATION

Run behavioral, adversarial and regression verification

Does the candidate behave correctly in relevant cases?

Input
Candidate revision, independent Verification Contract, original acceptance criteria, test suites, threat model, regression baseline.
Transformation / action
Run unit/integration/API/end-to-end tests, negative tests, authentication and authorization tests, failure/recovery behavior, privacy control tests, accessibility tests and DAST/penetration evidence as required. Verify test independence, not merely coverage percentage.
Deterministic responsibility
Reproducible test runners, differential tests, regression suites, mutation tests where mandated, runtime traces and coverage/quality metrics.
Where AI may help — bounded
AI may generate additional adversarial cases or suggest test gaps, but self-generated passing tests cannot be the sole independent basis of success.
Knowledge sources / packs
Verification patterns, requirements test catalogue, threat models, resilience KB, approval of required tests.
Schema / typed objects
TestExecutionEvidence · BehavioralFinding · NegativeCaseCoverage · RegressionResult
Output
Version-linked executed results plus explicit uncovered criteria, failures, missing tests and independence limitations.
Progression / decision gate

Failures/critical coverage gaps block. Missing essential test execution remains UNKNOWN rather than implicitly passing.

Failure path / loop

→ Governed repair of code or contract. Re-run the exact failing test and the appropriate regression perimeter.

Architecture note +

Separate “a test exists” from “the test ran successfully on this revision” and “the control works in production.”

14
INDEPENDENT VERIFICATION

Recheck actual impact against predicted impact

Did execution alter the solution boundary?

Input
Actual diff, runtime/config/schema changes, candidate dependency graph, baseline AffectedSystemSlice, allowed-file and interface lists.
Transformation / action
Compare observed modifications against the planned effect and architecture invariants. Check newly affected services, access paths, personal-data flows, third-party calls, event schemas, migrations and operational risk.
Deterministic responsibility
Actual-versus-authorized diff, dependency traversal, API/schema comparison, data-flow and permission-change detection.
Where AI may help — bounded
AI may propose the meaning of newly discovered interactions. The system must independently substantiate any material extension.
Knowledge sources / packs
System-model graph, architecture invariants, privacy/security rules, contract restrictions.
Schema / typed objects
ActualImpactAssessment · ScopeDelta · BoundaryChangeFinding
Output
Confirmed within-scope status or expanded impact set with new applicability implications.
Progression / decision gate

A material unplanned change invalidates the existing execution envelope and may invalidate both contracts.

Failure path / loop

→ Return to stage 04 (impact), 05 (applicability), 07 (contracts) and 09 (planning) as necessary.

Architecture note +

This is a structural CSCF distinction: the system can go back based on changed evidence without treating a development phase as completed forever.

15
INDEPENDENT VERIFICATION

Verify semantic claims and evidence quality

Do the sources actually support the claimed result?

Input
Candidate “implemented” claims, code/config references, test logs, scans, reviewer records and Verification Contract evidence obligations.
Transformation / action
Check each claim-to-source mapping. Reject fabricated locators, mismatched revisions, inferred implementation and unsupported assertions. Independent semantic reasoning is bounded to explicit evidence item, claim and requirement identifiers.
Deterministic responsibility
Citation/locator integrity, source hash/revision verification, type and status checks, coverage and provenance requirements.
Where AI may help — bounded
An independent AI verifier may challenge bounded claims. It cannot lock a finding on its own when deterministic prerequisites or human review are missing.
Knowledge sources / packs
Evidence policy, domain-specific validation questions, inference restrictions, contradiction rules, assurance instrument.
Schema / typed objects
VerifiedClaim · EvidenceQualityRecord · Contradiction · UnknownLedger
Output
SUPPORTED/PARTIAL/UNSUPPORTED/CONFLICTING/NOT_VERIFIABLE claim states with specific citations.
Progression / decision gate

Unsupported or conflicted decision-critical claims cannot satisfy an obligation.

Failure path / loop

→ Targeted source check, independent reviewer or additional test. Preserve unresolved claims as unresolved.

Architecture note +

Evidence ceiling: documentation may establish declaration; code may establish implementation; an executed test may establish tested behavior; only operational observation supports operating effectiveness.

16
INDEPENDENT VERIFICATION

Prove applicable policy requirements are implemented

Where is privacy, security and regulation “coded in”?

Input
Activated obligations, Implementation Contract, Verification Contract, source IDs and clauses, changed code/config, runtime configuration, executed evidence.
Transformation / action
For each applicable obligation, traverse the complete trace chain: source/authority → applicability fact → control → contract constraint → code/config enforcement point → test/scan/review evidence → finding → gate. Check control completeness and contradiction across functional and operational paths.
Deterministic responsibility
Exact-ID mapping, reference integrity, coverage status, required-check completion, control-state evaluation and mandatory-blocker rules.
Where AI may help — bounded
AI can propose mappings or semantic coverage gaps. It must not claim legal compliance based on fluent summaries or documentation alone.
Knowledge sources / packs
Security, privacy/GDPR, AI governance, accessibility, sector regulation, IP/data-use, customer policy packs; current normative source register.
Schema / typed objects
ControlTrace · ComplianceEvidenceMap · ApplicabilityCoverage · ControlFinding
Output
Obligation-by-obligation state: SATISFIED / PARTIAL / NOT_SATISFIED / UNKNOWN / NOT_APPLICABLE with evidence ceiling.
Progression / decision gate

Missing implementation, required test, reliable authority decision or a blocking control prevents release readiness.

Failure path / loop

→ Specific remediation, additional verification, formal exception or qualified human adjudication as applicable.

Architecture note +

For GDPR, sample enforcement points include access restrictions, minimization, retention/deletion, audit, purpose limitation and rights support as applicable. For AI, assess provider/tool permissions, traceability, human oversight, model behavior and relevant legal obligations. “Coded in” means an implemented enforcement mechanism corroborated by evidence, not a policy statement.

Control assurance is separate from solution quality

Security / privacy / AI / legal controls: show exact applicable obligations and current implementation evidence. Do not equate an accepted policy document with an implemented technical safeguard.

Purpose / product quality: stage 18 separately asks whether the result addresses the approved need.

ASSURANCE & ACCEPTANCE

Assurance & purpose

Verify both solution integrity and appropriateness

17
ASSURANCE & ACCEPTANCE

Select the required assurance scope

How much of the solution must now be reassessed?

Input
All verified findings, materiality, scope delta, incident/regulatory triggers, version boundary, active obligations and purpose impact.
Transformation / action
Always verify the local change. Expand to affected-system assurance if dependencies, trust boundaries, data flows or architecture are materially touched. Activate whole-solution assurance for lifecycle/purpose/autonomy/regulatory/material-release triggers according to policy.
Deterministic responsibility
Risk/materiality triggers, coverage accounting, finding-state evaluation, hard gate application and required-role lookups.
Where AI may help — bounded
Bounded AI reasoning may assist solution understanding and semantic claim verification. It does not decide whether required assurance can be skipped.
Knowledge sources / packs
Solution Assurance Engine A–F KB for AI-governance assessments where applicable; security/privacy/architecture policy packs; materiality policy.
Schema / typed objects
AssuranceScopeDecision · ChangeAssurance · AffectedSystemAssurance · WholeSolutionAssurance
Output
Scope selection with explicit justification and any expanded review requirements.
Progression / decision gate

A lightweight change is not forced through full reassessment, but a material control trigger cannot be bypassed for speed.

Failure path / loop

→ Expand assessment or obtain required authority where impact classification is disputed.

Architecture note +

For in-scope AI systems, full governance assurance can apply the six domains: A purpose/value/classification, B data/privacy/IP, C models/agents/providers, D security/robustness, E human impact/oversight, F accountability/evidence/lifecycle. Capability and anti-pattern evidence are assessed independently.

18
ASSURANCE & ACCEPTANCE

Check solution acceptance and purpose conformance

Did we build the right solution for the approved purpose?

Input
Approved purpose/value criteria, behavioral evidence, product/domain acceptance results, design and implementation facts, observed outcomes when available.
Transformation / action
Evaluate functional fit, usability/customer acceptance where relevant, domain outcomes, unintended effects, trade-offs, architectural alignment and approved usage boundaries. Keep technical compliance separate from product/value acceptance.
Deterministic responsibility
Contract acceptance-criterion coverage, outcome metric calculations, required approver and sign-off integrity.
Where AI may help — bounded
AI may summarize evidence and surface possible misalignment. It cannot decide an accountable business/ethical trade-off or approve a changed purpose.
Knowledge sources / packs
Purpose/value knowledge, domain acceptance rules, affected-person/UX criteria, customer acceptance obligations.
Schema / typed objects
SolutionAcceptanceRecord · PurposeConformanceFinding · OwnerSignoff
Output
Accepted, conditionally limited, rejected or awaiting owner/domain decision with traceable basis.
Progression / decision gate

A technically secure release can still be rejected if the approved purpose or domain acceptance fails.

Failure path / loop

→ Revise change intent or implementation; material purpose change requires renewed qualification.

Architecture note +

Pre-release tests verify bounded expected behavior. Real business value/effectiveness often needs post-release operational evidence.

Repair under tactics, then independently recheck

REMEDIATION LOOP

Classify findings and activate governed tactics

What can an agent fix, and what needs a human?

Input
Failed checks, locked findings, unresolved unknowns, materiality and authority limits, applicable tactic mappings.
Transformation / action
Map a finding to an approved tactic whose trigger, prerequisites, allowed executor, required evidence, prohibited uses, rollback limits and reassessment targets match the case. Route mechanical fixes to bounded tools/agents, sensitive changes to human review and authority decisions to humans only.
Deterministic responsibility
Finding-to-tactic exact IDs, prerequisite/approval checks, scope budget, exception routing and execution limits.
Where AI may help — bounded
AI can propose options or perform explicitly allowed fixes. It cannot choose its own acceptance condition, accept residual risk or mark a locked finding closed.
Knowledge sources / packs
Tactic Playbook, secure coding KB, exception/authority rules, verification patterns and control mappings.
Schema / typed objects
LockedFinding · TacticSelection · RemediationWorkPacket · HumanReviewRequest
Output
One bounded repair plan OR a required human action OR an explicit stop state.
Progression / decision gate

Only a new verified evidence cycle can change a finding. Tactic completion alone has no gate-clearing effect.

Failure path / loop

→ Rerun selected earlier steps: contract or plan gates if scope changed, execution if repair allowed, independent checks and assurance if evidence changed.

Architecture note +

Suggested route classes: AUTO_BOUND (lint/type), AGENT_PLUS_INDEPENDENT_TEST (clear defect), PLAN_PLUS_HUMAN_SECURITY_REVIEW (identity/crypto/data/IaC), HUMAN_DECISION_ONLY (risk exception, business purpose, production approval).

Governed return edges

Local defect → 09/10/11 and re-run 12–16. Scope or privacy/architecture change → 04–09. Requirements ambiguity → 01/06/07. Critical authority issue → hold for human decision. A tactic is not a gate waiver.

RELEASE & OPERATION

Assemble the readiness package and evaluate release gate

May this exact version be promoted into its target environment?

Input
Contract reports, security/privacy/regulatory control findings, assurance scopes, test/scan evidence, approved exceptions, owner decisions, deployment artifacts.
Transformation / action
Create a canonical readiness package for the exact revision. Enforce completion of critical controls, independent review, accepted risk/exception decisions, deployment/rollback conditions, supply-chain provenance and solution acceptance. Generate human-readable rationale from locked results only.
Deterministic responsibility
Gate rules, artifact/hash/version consistency, required signatures, approver identity checks, risk policy and evidence completeness.
Where AI may help — bounded
AI may explain findings or draft a report. An AI narrative cannot raise assurance, clear a hard gate, accept residual risk or authorize release.
Knowledge sources / packs
Release control pack, operations KB, risk-acceptance policy, compliance and assurance findings.
Schema / typed objects
ReadinessPackage · GateDecision · ReleaseAuthorization · ExceptionDecision
Output
PASS / REWORK / BLOCK / ESCALATE with attributable release approval and bounded deployment target.
Progression / decision gate

A report being publishable and a system being deployable are distinct decisions. Named authority must approve where policy requires.

Failure path / loop

→ Rework the specific failure or obtain a valid authorized exception, then re-evaluate all affected gates.

Architecture note +

Human sign-off does not substitute for mandatory objective evidence. A green technical score cannot average away one explicit blocker.

RELEASE & OPERATION

Deploy under authorization and preserve rollback

Is the released artifact identical to the assessed candidate?

Input
Authorized ReadinessPackage, signed build/image, SBOM, target environment, deployment controls, rollback and monitoring plan.
Transformation / action
Use controlled CI/CD to verify artifact signatures and environment permissions, deploy the exact assessed revision, monitor rollout signals and preserve the decision/audit record. Separate generator, reviewer, authorizer and deployment pipeline roles according to policy.
Deterministic responsibility
Signed artifact verification, policy-as-code for environment, change-ticket binding, deployment/rollback execution and audit trail.
Where AI may help — bounded
AI can assist deployment analysis and incident triage, but does not self-authorize production deployment.
Knowledge sources / packs
Deployment/release policy, secrets and environment standards, operations runbook, continuity/incident KB.
Schema / typed objects
DeploymentRecord · ArtifactProvenance · RollbackRecord · RuntimeVersion
Output
New deployed version tied to its original evidence package, or rollback/failed-release finding.
Progression / decision gate

Unmatched artifact, unsigned mandatory package or unauthorized environment causes hard BLOCK.

Failure path / loop

→ Stop deployment, revert/rollback if required, open incident and reassess.

Architecture note +

The reviewed source revision, binary/image and deployed runtime identity must be linked. Otherwise pre-release evidence might not apply to what was deployed.

PRODUCTION LEARNING

Collect operational evidence and reassess claims

Does observed operation match predicted behavior?

Input
Runtime telemetry, access/audit logs, outcome metrics, incidents, defects, drift signals, customer feedback, vulnerability feeds, policy and provider changes.
Transformation / action
Bind new observations to runtime version, operating boundary and assessed claims. Detect regressions, data-purpose drift, model/provider changes, control failures and unmet outcome hypotheses. Apply event/periodic reassessment triggers.
Deterministic responsibility
Alert thresholds, telemetry validation, drift/change detectors, SLA and incident policy, version-aware evidence aggregation.
Where AI may help — bounded
AI may cluster incidents, propose hypotheses and summarize observations, but must distinguish causal proof from speculation.
Knowledge sources / packs
Operations and resilience KB, runtime control definitions, approved risk signals, purpose/value metrics, monitoring obligations.
Schema / typed objects
OperationalEvidence · DriftFinding · IncidentTrigger · ReassessmentRequest
Output
Evidence-backed operating status plus new findings, alerts and controlled change triggers.
Progression / decision gate

Operational facts may strengthen, contradict or downgrade prior assurance. Silence is not proof that a control is effective.

Failure path / loop

→ Immediate containment for severe incidents or a new ChangeIntent / scope reassessment for material changes.

Architecture note +

Only production evidence can establish a bounded claim of operational effectiveness. Deployment is the beginning of the next evidence cycle, not the end of verification.

PRODUCTION LEARNING

Validate learning and update the system model

What becomes part of the next accepted reality?

Input
Operational evidence, accepted code/runtime state, verified findings, defect escape analysis, tactic performance and candidate learning.
Transformation / action
Challenge new conclusions for quality, source lineage, contradictions, durability and significance. Update SystemState and approved knowledge/policy/tactics only through authorized change rules. Keep policy updates separate from unreviewed agent memory.
Deterministic responsibility
Learning-schema validation, evidence thresholds, contradiction checks, version diff, knowledge approval and golden-case regression.
Where AI may help — bounded
AI may propose lessons, detect recurring patterns or draft changes to tactics. Learning candidates cannot silently modify the governing cognitive model.
Knowledge sources / packs
System-model KB, evidence ledger, control/tactic version history, quality metrics and creation-system evaluation corpus.
Schema / typed objects
ValidatedLearning · SystemStateVersion · KnowledgeChangeProposal · NextChangeTrigger
Output
New accepted evidence-backed solution state and, where separately approved, updated creation-system knowledge.
Progression / decision gate

Unverified observation or AI explanation stays a candidate, not authoritative knowledge.

Failure path / loop

↻ Future change returns to stage 01 using updated versioned state, evidence and approved control knowledge.

Architecture note +

Learn from the system that made the change as well: recurring false fixes, unnecessary human escalations, gate escapes, poor test coverage and drift can reveal weaknesses in CSCF itself.

Persistent lanes that run alongside every node

These are not additional waterfall stages. They are maintained services and evidence/authority boundaries consulted repeatedly throughout the vertical flow.

01 / Solution state and evidence ledger

Version-specific code/configuration reality, repository and architecture graph, system invariants, requirements, approved releases, source locators, observations, claims, contradictions, missing evidence, and the complete decision chronology. Facts are typed, not flattened into generic “context”.

02 / Canonical Knowledge Base and normative sources

Source register, stable rule IDs, current editions, jurisdiction/effective date, allowed interpretation, exclusions, applicability predicates, engineering standards, security/privacy/AI governance/control packs, coding and architecture standards, human-impact and customer/domain requirements. Human-readable references and machine-operable knowledge are related but not interchangeable.

03 / Cognitive model and deterministic kernel

Evidence acceptance, epistemic states, applicability compilation, contract readiness, executor routing, permissions, independent verification duties, non-bypassable gates, remediation state machines, authority rules, rollback and accepted state transitions. AI may serve individual bounded reasoning tasks, but deterministic control logic remains inspectable and separately testable.

04 / Tactic Playbook and authorized remediation

Maps a verified finding to precise corrective work. Each tactic has prerequisites, allowed executor, do-not-use boundaries, risk limits, acceptance criteria, verification method, human review trigger and reassessment targets. Tactic execution creates candidate work and new evidence, never an automatic finding closure.

05 / Named human authorities

Product/domain owner decides purpose and relevant acceptance. Security/privacy/legal authorities resolve their own scoped review or exceptions where required. Reviewers independently validate sensitive code/tests. Release approvers authorize production. These are decision rights, not a generic “human in the loop” checkbox.

06 / Operational monitoring and creation-system QA

Production evidence evaluates the delivered solution. Defect-escape analysis, false-fix rates, gate failures, tactic success and agent/tool quality also evaluate CSCF itself. Accepted learning updates the system model; changes to rules and tactics follow their own versioned approval gates.

Representative machine-readable contracts

The code below illustrates object boundaries and decision semantics. Names and exact schemas are proposed, not frozen specifications.

Example A — applicability activates implementation and proof
rule_id: PRIV-APP-004
source_ref: SOURCE-ID / exact-clause-locator / version
when:
  change.processes_personal_data: true
then:
  activate: CONTROL_PACK.PRIVACY
  add_to_implementation_contract:
    - enforce approved purpose and access boundary
    - enforce retention / deletion requirements
    - protect data flows and audit access
  add_to_verification_contract:
    - verify authorized / unauthorized access
    - verify retention and deletion cases
    - inspect data flow and audit evidence
  reconsider_when:
    - material data-flow change
    - jurisdiction, purpose or actor-role change
    - before release
if_applicability_unknown: ESCALATE_OR_RESTRICT

Purpose: demonstrate how one approved normative rule becomes obligations in both contracts and later becomes independently testable.

Example B — dual contracts from one approved requirement
change_id: CHG-1042
approved_requirement: REQ-ADDRESS-CHANGE
implementation_contract:
  allowed_scope: [order-service, address-update-api]
  invariants: [order-state-rules, authorization]
  prohibited_change: [payment-settlement-schema]
  deliver: [patch, changed-file-list, assumption-ledger]
verification_contract:
  tests: [valid-order-state, invalid-state,
          ownership-check, audit, regression]
  evidence: [test-results, API-diff, SAST, DLP-check]
  verify_against_revision: exact_commit_hash
  required_independence: true
readiness: CONTRACT_READY only after checks

The execution agent cannot redefine the verification branch as a way to make its own patch pass.

Example C — coding adapter input/output
execute(
  implementation_contract,
  relevant_system_slice,
  tool_policy,
  repository_access
) -> ImplementationResult

ImplementationResult:
  execution_id
  commit_hash / patch_hash
  changed_files / changed_interfaces
  requirement_mappings
  tests_added / test_origin
  assumptions / unresolved_questions
  dependency_changes / security_relevant_changes
  tool_audit / provenance

The packet may be translated into executor-specific prompts or APIs. What counts as valid evidence and release readiness stays outside the adapter.

Example D — finding → tactic → new evidence → reassessment
finding_id: FIND-SEC-028
status: NOT_SATISFIED
tactic_id: TAC-SEC-SECRET-ROTATION
trigger: verified embedded secret
allowed_executor: agent_for_code_cleanup + human_security_review
prerequisites: isolate/revoke exposed secret
acceptance:
  - secret removed from current code and history as required
  - rotation evidence from authorized system
  - scanner re-run on assessed revision
closure_effect: NEW_EVIDENCE_AND_REVERIFY
next_state: decided_by_kernel_after_independent_checks

The tactic does not set status to SATISFIED. Its output is re-acquired and independently assessed.

Example E — proof chain and conservative assurance states
source_ref -> applicability_fact -> active_obligation
           -> implementation_constraint
           -> enforcement_point(code/config)
           -> executed_test_or_review
           -> verified_finding -> gate_decision

Evidence ceiling:
  DECLARED != IMPLEMENTED
  IMPLEMENTED != TESTED
  TESTED != OPERATIONALLY_OBSERVED

Missing proof -> UNKNOWN, not PASS
Authorized exception != proof of control effectiveness
Signed approval != test evidence

An auditable chain should work backward too: every decisive test or review should identify the obligation that demanded it.

Where quality, purpose and regulatory controls are proven

“Coded in” must be demonstrated at more than one level. The review connects approved requirements to actual code/configuration and to executed, attributable evidence.

Security, code integrity and supply chain

Obligations at 05–07. Threat model, secure defaults, least privilege, credential handling, dependency and artifact policies become explicit contract constraints. Proof at 12–16. Compile/types, secure coding analysis, SAST, SCA, DAST, secrets/IaC/container checks, SBOM, adversarial tests, actual-change impact, approved human review and signed artifact linkage run as applicable. Release at 20–21. Required failures remain blocking until verified remediation or a formally permitted exception.

GDPR, privacy and sensitive data

Applicability at 04–05. Identify processing, purpose, roles, jurisdiction, categories of data, data subjects, third parties and relevant legal bases/obligations. Implementation at 07–11. Encode relevant minimization, purpose limitation, access, retention, confidentiality, transparency and rights-handling requirements into constraints and design. Proof at 13–16. Executed access/retention/data-flow tests, configuration checks, audit evidence and needed privacy/legal review. A formal DPIA is required when the applicable legal/policy threshold says so; the existence of personal data alone is not a universal legal DPIA trigger.

AI systems, models and agentic operation

Applicability at 05. Classify whether the delivered solution is an AI system, identify actor role, intended use, affected people, autonomy, provider/tool relationships and exact applicable obligations. Controls at 07–11. Bound model/agent permissions, inputs, tool access, output validation, oversight, logging, provider and supply-chain restrictions. Proof at 13–17. Representative behavior and adversarial tests, traceability and affected-person controls, evidence-bounded A–F assurance where applicable. An AI model’s confident claim cannot change a locked finding or establish legal compliance.

Other legislation, standards and customer obligations

Authority at 05. Each obligation must carry a verified normative identity, time/jurisdiction/actor applicability and exact mapping. Requirements differ for security, accessibility, intellectual property, consumer/product, sector and contractual commitments. Enforcement at 07–16. Only controls with concrete implementation and verification obligations become “coded in”. Legal interpretation, authorized exceptions and compliance claims keep their required human authority boundary.

Purpose, functional behavior and user/customer value

Qualification at 01 and 06. Approve desired outcome, baseline, permitted uses and success conditions. Proof at 13 and 18. Passing tests answers “built as specified.” The separate Solution Acceptance Gate answers “was the right solution built?” Learning at 22–23. Outcome evidence may arrive only in production and can revise accepted assumptions.

Worked route: delivery-address change

A compact illustration of why CSCF cannot be reduced to “prompt → code → test → release”.

Intent / 01 → 06

“Customers should be able to update a delivery address after creating an order.” The system identifies order-state restrictions, ownership, fraud/tax, fulfilment, downstream messages and audit. A domain owner approves the allowed use cases and outcome.

Contracts / 07 → 08

The Implementation Contract permits bounded changes in the address flow and protects payment and authorization invariants. The independent Verification Contract requires valid/invalid order-state tests, ownership denial, audit, regression and relevant privacy evidence. Only then does the kernel mark CONTRACT_READY.

Agent / 09 → 11

A suitable coding adapter receives only relevant code, approved constraints, bounded tool permissions and the expected result schema. It produces the patch and reports any dependencies it discovered. It cannot grant itself more repository scope.

Unexpected scope / 14 → 05 → 07

If the patch changes an event schema or authentication middleware, actual-impact comparison detects the newly touched trust boundary. The earlier impact analysis is reopened, additional applicable controls are activated and contracts are reconstructed. The previous plan is not allowed to authorize that expansion retroactively.

Verify, accept and release / 12–21

Structural and behavioral evidence is independently checked. Relevant authorization/privacy controls are mapped to code and executed tests. The solution owner separately accepts the customer behavior. A current readiness package governs authorized deployment.

Operate and learn / 22–23

Real usage, support tickets, failed permission checks and downstream errors become new evidence. Only validated conclusions update the system model and may initiate the next change.

What the blueprint does and does not establish

Established conceptual decisions

One evidence-gated kernel, two intake modes, bounded system slice, application of explicit control packs, independently derived Implementation and Verification Contracts, agent-agnostic execution, independent checks, scoped assurance, tactics with re-verification, human authority, release conditions and validated learning are directly aligned with the current CSCF concept.

Detailed architecture still to be finalized

Production schemas and IDs, executable policy language, exact access-control architecture, legal-source freshness processes, test thresholds and scanner profiles, customer-specific exceptions, decision-engine proof semantics, agent sandbox implementation, monitoring events, service boundaries, operating SLOs, authorization delegation, tactic approval lifecycle and state-store technology require concrete design and testing.

Evidence required to claim implementation

A working repository and codebase, evaluated golden/failure cases, real release gate tests, rule-to-code coverage and false-negative analysis, data-handling assurance, production-like executor sandbox evaluation, signed evidence retention, human decision controls, and actual operational feedback. The architecture in this HTML is a proposed reference blueprint, not evidence that CSCF currently satisfies any legal standard or secure-development requirement.

Design integrity checklist for the first prototype
  • One end-to-end change with a typed current-state object, two contracts, and a repeatable decision gate.
  • At least one activated security control and one privacy applicability case with exact source-to-test traceability.
  • An agent or human adapter that cannot authorize its own success.
  • A failing test that routes to an exact tactic and is re-verified without automatic finding closure.
  • An unexpected-scope patch that reopens impact analysis before authorization.
  • A deliberately missing source that stays UNKNOWN and blocks an unsafe transition.
  • A release artifact whose hash links the evidence package to the deployed version.
  • One production observation that creates candidate learning and is approved before updating SystemState.

Basis: the current CSCF master concept and its control/tactic refinements, the supplied solution assurance thinking flow, and secure-development control principles translated into technology-neutral obligations.
